# 006 — Architecture and design

Status: Draft for review; application code remains unchanged. Requirements and acceptance IDs are defined in the companion documents.

## Existing foundations and dependencies

Reuse `App\Models\User`, `Faq`, `ChatbotQuestion`, `App\Chatbot\FaqService`, `FaqNormalizer`, and the installed Laravel web guard. Feature 005 is implemented in this working tree, not assumed merely from its specifications. Its deployment and external acceptance are unverified. The 005 service lacks FAQ deletion, so 006 will add a minimal revision-checked transactional delete operation to that service. Keep its console callers compatible.

Only a new default-false `users.is_chatbot_admin` column is proposed. Exclude it from mass assignment; provisioning must explicitly set it through an authorized console operation. Do not duplicate FAQ/question tables, add visitor profile fields or change status meanings. Existing sessions have IP/user-agent columns: admin session use is a separate security/privacy purpose requiring policy review, not permission to collect visitor chatbot identities. Do not expand baseline session metadata or copy it into question records.

## Authentication and authorization

Add Blade login at `GET /admin/login` (named `login`), CSRF-protected `POST /admin/login`, and authenticated `POST /admin/logout`. Use the existing session guard, Laravel password hashing and generic login errors for unknown accounts, wrong passwords and non-admin accounts. Do not establish an admin session for a non-admin. On successful login regenerate the session ID; logout invalidates the session and regenerates the CSRF token. No remember-me. Admin-scoped middleware enforces 30-minute idle and 8-hour absolute expiry without changing unrelated site session lifetimes. All private responses, including login/error responses, are no-store.

Provide restricted `chatbot:admin:create`, `chatbot:admin:grant <user-id>`, `chatbot:admin:revoke <user-id>` and `chatbot:admin:password-reset <user-id>` Artisan workflows. Reuse 005 `OperatorAccess` as the console authorization boundary only: protected prompts, explicit confirmation, individual operator audit and no credentials in arguments/output/logs. Create collects only necessary admin name/email/password; confirm password through hidden input, hash it, and validate against the configured hashing algorithm (including bcrypt's byte limit). No seed/default account. Grant/revoke do not implicitly create accounts. Password reset/revocation invalidate existing target sessions; authorization also reloads the admin capability on every request. Production OS/IAM authorization remains an external gate.

Group `/admin/chatbot/**` under `web`, `auth:web`, admin-session expiry and `can:access-chatbot-admin`; apply `FaqPolicy`/`ChatbotQuestionPolicy` to each operation. Check broad access before resource lookup to prevent non-admin existence disclosure. Policies allow admins the specified actions only; there is no question update action. Guest pages redirect to the local named login route; JSON requests receive 401. Authenticated forbidden requests return 403. Missing resources return 404 only after authorization. Restrict intended redirects to local admin paths.

Deletion additionally requires CSRF, an explicit confirmation flag and an admin password confirmation no older than 900 seconds. A protected confirmation endpoint verifies the current user's password with the same account/IP login quotas. Expired confirmation returns a safe actionable error; cancellation writes nothing. Never put credentials in query strings or retain plaintext in sessions.

## Pages and private data contracts

Blade owns layout/navigation and ordinary page links. Vue islands supply metric loading, table search/filter/cursor navigation, forms and accessible dialogs. Use the current Vite entry and conditional admin mounting; no SPA router, Inertia or separate frontend. Login can use ordinary Blade forms. Existing chatbot mounting remains restricted to its existing host page.

| Route within `/admin/chatbot` | Purpose |
| --- | --- |
| `GET /`, `/questions`, `/questions/{id}`, `/faqs`, `/faqs/create`, `/faqs/{id}`, `/faqs/{id}/edit` | Authorized page shells/details; create may use an internal `source_question_id`, never question text in the URL |
| `GET /data/metrics` | Four aggregate counts |
| `POST /data/questions/search`, `/data/faqs/search` | Read-only search/filter/cursor results; body rather than URL keeps sensitive searches out of access URLs; CSRF required |
| `GET /data/questions/{id}`, `/data/faqs/{id}` | Explicit field allowlists |
| `POST /data/faqs` | Validated inactive create; optional authorized source row ID |
| `PATCH /data/faqs/{id}` | Revision-checked content edit |
| `POST /data/faqs/{id}/activation` | Explicit boolean target state, expected revision and confirmation |
| `DELETE /data/faqs/{id}`, `/data/questions/{id}` | Confirmed authorized deletion; recent password required |
| `POST /password/confirm` | Recent-password verification; no credential echo |

These are authenticated web routes, including JSON responses; none belongs in the stateless public API group. The login screen is necessarily guest-accessible, but no management operation is public. Do not expose an Artisan execution endpoint.

Question DTO: internal `id`, `question`, original `status`, `created_at` in ISO UTC and optional original matched FAQ internal ID. Do not serialize entire Eloquent models: session_hash, request_id and other unneeded fields must never enter HTML/JSON. FAQ DTO: `id`, `question`, `answer`, `is_active`, UTC timestamps and the existing server-generated revision. Do not expose normalized keys. Metrics count current retained rows, not searches or lifetime collection. Originally unanswered counts do not decrease merely because an FAQ is prepared.

Lists use cursor ordering `(created_at,id)` ascending for questions and descending for FAQs, with default 25/maximum 50 rows. Use bounded validated opaque cursors containing only ordering fields; cursor advancement must tolerate concurrent purge/deletion. Search accepts an optional trimmed string up to 200 Unicode code points, literal substring only, with `%`, `_` and escape characters escaped in bound LIKE expressions. Use MySQL 8.4 `utf8mb4_0900_as_ci` for explicitly case-insensitive/accent-sensitive administrative search, independent of 005 binary normalized matching. Validate status/active filters against fixed enums and do not accept arbitrary SQL sort/columns. Read only a page plus one row; no unbounded relation loading/export. Exact aggregate counts use SQL aggregates without hydrating text. Search can require scanning text; index-supported filters/cursors and request quotas bound exposure, while representative-data performance is a release check rather than a claim that LIKE has a full-text index.

## Write and lifecycle contracts

Validate strict input types and exact field allowlists before shared Unicode validation. FAQ bounds remain 1–1,000 question and 1–4,000 answer code points under 005 rules. Pass only question/answer to `FaqService::create/update`; never mass-assign active state, revision-derived fields or admin privileges. Shared model/service normalization remains the only source of match keys. Duplicate normalized keys, including inactive rows, fail without inserting/updating another record.

Creating from a question reads an authorized retained row and prefills an editable question with an empty answer. No FAQ exists until Save. Show a warning to remove personal details before publication. Saving does not update/link/reclassify the source row. If the source was purged before Save, return 404 and preserve the local form so the admin can deliberately create a standalone FAQ after reviewing it.

For edit/activation/deactivation, reuse the existing canonical revision under the service's transaction and row lock. Add deletion with the same expected-revision contract. A stale revision returns 409 and changes nothing, including when another administrator or Artisan operator changed the row. Offer reload/current-version comparison; never silently overwrite or automatically resubmit. Duplicate-key conflict also uses 409 with a distinct safe error code. Validation uses 422, CSRF failure 419, body cap 413, quota 429 with Retry-After, dependency outage 503 and unexpected failure a generic 500. Successful creation returns 201; updates return 200/current DTO; deletion returns 204. Missing rows return authorized 404. No error echoes supplied text, SQL or traces.

Changed FAQ content atomically becomes inactive; an actual no-op preserves activation. Explicit activation previews the current validated content and uses its revision. Deletion sets existing question `faq_id` to null through the established FK without changing original status/timestamps. Public replays continue 005 semantics: original answers may fall back after removal; original misses can receive newly active answers while remaining originally unanswered. No answer snapshots or new classification writes.

Question deletion is a narrowly authorized hard delete by internal row ID, with row locking and no content edits. Concurrent purge yields a safe 404/refreshed list. Before deleting, record a protected restoration instruction containing only row ID, original creation timestamp and deletion timestamp (not text, hashes or request IDs); if durable recording fails, fail closed without deleting. Store these records in a private restricted metadata audit sink separate from ordinary logs, retained for the backup lifetime (30 days). Production must keep this sink available independently of restored database backups and reapply deletions and the 005 age purge before exposing restored service. Local app tests use a private fake sink and prove ordering/failure behavior; they do not prove independent backup durability. Define the production sink/runbook before release; do not add a backup engine. The existing 90-day UTC cutoff, daily bounded purge and normally-within-91-days live retention remain unchanged.

## Request security and deployment compatibility

Installed routing uses the standard web session/request-forgery middleware. Keep Laravel 13's installed `PreventRequestForgery` behavior; do not disable it for private JSON or search. Native fetch uses same-origin credentials, Accept JSON and a Blade-issued CSRF token; session expiry retains unsaved content only in page memory and never automatically retries a write. No local/sessionStorage of private question/answer content, no `v-html`, Markdown execution or unsafe inline bootstrap strings. Escape Blade output and use framework-safe JSON encoding for minimal bootstrap route/CSRF configuration. UI confirmations do not replace policies/server checks.

005 `ChatbotBoundary`, exact-Origin validation, early 16 KiB body cap, privacy exception handling and custom proxy behavior are scoped to `/api/chatbot/questions`. They do not automatically protect admin routes. Add an admin-scoped early bounded body guard (32 KiB, actual bytes including absent/incorrect Content-Length) before JSON parsing/transformations; exempt FAQ/search fields from incompatible default trim/null transformations only on these routes. Login HTML bodies and JSON both obey this cap. Keep password values untrimmed. Preserve all public endpoint limits/ordering. Add safe admin exception reporting and no-store even for early rejection; do not flash question/answer input or log query bindings/payloads.

Use independent atomic Redis counters on the explicit configured chatbot Redis connection, with separate `admin-login-account`, `admin-login-ip` and `admin-request-user` domains. HMAC account/IP keys; user keys contain only internal IDs. Fixed first-acquisition 60-second windows, bounded expiry at most 120 seconds, no shared-cache fallback. Login/password-confirmation quotas are 5/account and 20/IP; authenticated request quota is 120/admin. Redis outage fails closed before login success or mutations. Proxy spoofing must not bypass the IP quota. Inspect the installed proxy middleware for admin paths and configure explicit trusted proxies/header masks or explicit no-proxy local behavior; preserve 005 configuration and do not assume its endpoint-scoped trust applies here.

Production gates: HTTPS, Secure/HttpOnly/SameSite session cookies, actual proxy/header/direct-access topology, ingress/PHP body limits and pre-Laravel errors, private MySQL/Redis, attributable console provisioning and restricted durable audit storage. Redact bodies/searches/credentials in reverse proxy/APM/debug tooling, not just application logs. Audit only verified actor ID, action, resource ID, outcome and UTC time; deletion restoration metadata uses the separate protected sink. Login audit excludes email/IP/credentials. Session cleanup and admin identity retention require security/privacy ownership; do not change visitor privacy notice silently.

## Presentation and verification boundaries

Use existing typography/colors/spacing conventions for a distinct admin layout without modifying chatbot CSS/classes. Collapsible mobile sidebar has a labeled button, keyboard interaction, Escape and restored focus; modal confirmations trap/restore focus. Tables have headings, associated filters, accessible status text and keyboard-operable actions. Forms associate errors with fields; submission disables duplicate actions and provides polite loading/success announcements and actionable errors. Preserve line breaks and wrapping of literal content. Verify 320×568 and 1440×900, 200% zoom, reduced motion, keyboard and real screen-reader use.

Reuse dedicated `compose.chatbot-tests.yaml`, `IsolationGuard` and `ChatbotTestCase`; extend the harness to create needed users/sessions and 006 migration only after validated test identity. Existing helper loads only `*chatbot*.php`, so auth fixtures cannot be assumed present. Negative guard tests must run before any DB/Redis/session connection. Every parallel connection, session backend and limiter must remain on owned isolated services/schema/namespaces. No migrate:fresh, DROP, flush, shared cache clear, development seeding or volume deletion. Use synthetic questions/accounts and owned transactions/keys. Record red/green chronology and pre-change baseline at implementation time; never reconstruct missing historical 005 evidence.

Application test results, actual browser observations, production infrastructure evidence and privacy approval are separate records. Draft specifications and static inspection pass none of these gates.

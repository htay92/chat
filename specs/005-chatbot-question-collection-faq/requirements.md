# 005 — Chatbot question collection and prepared FAQ answers

Status: Application implementation approved explicitly by the user in this session. Application implementation and automated verification recorded in [evidence](evidence/application.md); manual, production infrastructure and privacy-policy release gates remain pending.

## Scope, dependencies, and precedence

Extend the existing Laravel website and Vue 3 Composition API/TypeScript widget with MySQL question collection and deterministic database-backed FAQ replies. Preserve the implemented Minimal SaaS UI from [004](../004-chatbot-minimal-ui/requirements.md) and interaction baseline from [001](../001-chatbot-widget/requirements.md). Existing manual acceptance gaps and the pending speaker-name amendment remain unresolved by this feature.

After approval, this feature supersedes only their local-mock default, fixed 500 ms delay, no-chat-network/no-persistence exclusions, and mock-specific notice/error wording. Keep injected responders and local mocks for isolated tests. Do not overwrite older specs or claim approval of their outstanding amendments. Use existing Vite configuration, Laravel Sail, MySQL, Redis, PHPUnit and Vitest.

Excluded: AI providers/SDKs/credentials, embeddings, fuzzy or semantic matching, streaming, authenticated conversations, admin UI/API, public history/search/export/deletion endpoints, attachments, tracking/analytics, email capture, and redesign. This feature includes restricted Artisan FAQ management and read-only unanswered-question review. A browser admin UI, review assignments, workflow statuses, bulk export and public management endpoints require a separately approved follow-up specification.

## Requirements

- **R-01 — API:** Provide same-origin `POST /api/chatbot/questions` accepting JSON `question`, `session_id`, and `request_id`. Return JSON only. No visitor login or AI service is required. Success is returned only after persistence commits.
- **R-02 — Validation:** Trim question edges using the same Unicode whitespace policy on client/server. Accept 1–1,000 Unicode code points after trimming; preserve internal spacing/newlines in stored question text. Require canonical UUID v4 identifiers; reject missing, invalid, non-string or extra fields. Limit request body to 16 KiB. Reject invalid input without creating question rows or echoing submitted values in errors.
- **R-03 — Anonymous scope:** Generate a random UUID v4 per browser tab, stored only in sessionStorage with an in-memory fallback if storage is unavailable. Reuse through same-tab reloads; no cross-tab coordination or durable localStorage. Rotate after 24 hours, before a new exchange; retries retain their original session/request identifiers. This is pseudonymous grouping, never authentication or proof of visitor identity. Store only a server HMAC of the session UUID, not its raw value.
- **R-04 — Collection:** Persist one row per accepted logical submission, including question, hashed session, request UUID, answered/unanswered status, nullable matched FAQ ID, and UTC timestamps. Store neither assistant answer snapshots nor IP, user agent, referrer, page URL, name, email, account ID or device fingerprint. A repeated intentional question with a fresh request UUID is a separate row.
- **R-05 — FAQ:** Store FAQ question, normalized match key, prepared plain-text answer, active flag, and timestamps in MySQL. Questions meet R-02 limits; answers are nonblank and at most 4,000 code points. Require unique normalized keys, including inactive entries. Supply a small explicitly fictional/demo seed set through an opt-in, non-destructive seeder, never automatically in production. Provide operator-only Artisan create/update/activate/deactivate/list/show commands. Operators authenticate through individually assigned, authorized OS/SSH or deployment IAM accounts; Artisan itself is not a login boundary. Restrict console/container execution to those accounts. Create inactive; editing question/answer forces inactive, followed by explicit activation after preview/confirmation. Use protected prompt/stdin for content, validated atomic writes, duplicate-key rejection and optimistic concurrency checks. Audit operator identity/action/FAQ ID/time/outcome without content or visitor identifiers. No public management endpoint; no arbitrary operator-name flag as authentication.
- **R-06 — Matching:** Compare normalized exact strings: Unicode NFC, trim, collapse Unicode whitespace runs to one ASCII space, then locale-independent Unicode lowercase. Do not remove punctuation, accents or words; do not use substring, similarity or AI matching. Only active FAQs match. A match returns the current prepared answer and records answered; no match records unanswered and returns exactly “Thanks for your question. We don’t have a prepared answer for that yet.” A fallback is a successful reply, not a transport error or a promise of human follow-up.
- **R-07 — Retry consistency:** A unique `(session_hash, request_id)` prevents duplicate rows on retries/concurrent requests. Same key and same trimmed question returns the original stored classification with a current reply, without reclassifying it; different question returns 409. If an originally matched FAQ is edited/deactivated/deleted, replay returns its current answer only if still active, otherwise fallback, while preserving the original collection status. An originally unanswered row may return a newly created/activated matching FAQ on replay, but remains unanswered with faq_id null. `status` always means classification at first acceptance; `reply_source` describes only the current returned text. Neither implies human review or completion. No historical answer snapshots are retained. Deduplication lasts only while the row is retained; retries after deletion can create a new row.
- **R-08 — Review readiness:** Provide a read-only operator-only Artisan review command in this feature, using the same authenticated server-access boundary as R-05. Page originally unanswered rows oldest-first by `(created_at, id)`, with a maximum of 50 rows per page and explicit continuation cursor. Show only internal row ID, creation time and safely escaped question text, not session_hash/request_id. Neutralize terminal control sequences. Reviewing or preparing an FAQ does not change original question status, add review fields or promise follow-up. Matched FAQ deletion nulls its reference without deleting collected questions or changing original status. No public access to collected questions, FAQ management or review operations. Future web administrative access and any mutable review workflow require a separately approved specification.
- **R-09 — Abuse protection:** Use a dedicated Redis connection and atomic acquisition, independent of default CACHE_STORE; no fallback to array/database cache. Redis-backed fixed-window limits: 10 POST attempts/minute per session hash and 30/minute per HMAC-derived client IP, applied before validation/persistence; malformed or missing session IDs still consume the IP limit. Return 429 with Retry-After; consume attempts on replay too. IP-derived keys are transient, expire within two minutes, and never enter MySQL/logs. Trust forwarded IP headers only from configured explicit proxy addresses/CIDRs and expected header masks; do not accept wildcard trust or infer trust from user-supplied Host. Verify application middleware ordering and the actual proxy topology before deployment. Each valid-Origin, within-size JSON POST consumes the IP attempt first, then the session attempt if the UUID is valid, including validation failures/replays; Origin/size/content-type rejections do not enter the limiter. Redis failure fails closed with 503 and no write.
- **R-10 — Safety/privacy:** Accept anonymous traffic without ambient cookies/authentication, use same-origin browser requests and no permissive CORS. Permit POST only for a separately configured canonical site Origin (local scheme/port may differ from production; never infer it from Host/forwarded headers); reject missing/unapproved Origin. Use parameterized database operations, plain-text Vue interpolation, and no v-html/Markdown. No question/session/request body capture in application, proxy, APM or exception logs. Return generic failures with no SQL, stack traces or submitted text. Application safeguards and deployment safeguards have separate acceptance records. Deployment must use HTTPS and restricted database/console access; production ingress caps, trusted proxy topology, logging/APM redaction and privacy-policy approval are release gates, not claims established by unit tests. Questions may themselves contain personal data; do not describe them as guaranteed anonymous.
- **R-11 — Notice:** Replace the mock notice with “Demo FAQ answers. Questions are normally deleted within 91 days to improve FAQs. Don’t include personal or sensitive information.” Preserve notice styling and accessible readability. Keep Demo title/badge; replace the mock failure copy with “Could not send your question. Please try again.” No claim that an AI answered or a human will reply. The privacy owner must approve the full policy covering pseudonymous identifiers, user-entered personal data, access, early deletion limits, schedule failures and backup expiry. The brief widget notice does not replace that policy.
- **R-12 — Retention/deletion:** Delete all collected rows, answered and unanswered, at `created_at <= now UTC minus 90 days` in a daily scheduled, bounded-batch purge. Fixed policy applies to original creation, not last retry. Operational maximum is 91 days with a healthy daily scheduler; monitor failed/missed runs. Provide an operator-only deletion command by exact session UUID (hash internally, no token in logs) for early deletion; no public deletion API or identity verification is promised. Deletion is hard deletion including the deduplication record. FAQ records follow owner management, not question retention. Backups expire within 30 days, stay access-restricted, and purges/early deletions must be reapplied before restored data is served.
- **R-13 — Widget compatibility:** Swap the production responder for the API adapter; retain theme, geometry, icons, avatars, names, mount scope, draft/transcript in memory, validation, keyboard/IME, one pending exchange, scrolling, accessibility, focus, close/reopen and unmount protection. Each logical send gets a new request UUID; Retry reuses failed exchange IDs without another user bubble. Use a 15-second timeout; errors/invalid JSON/non-2xx enable Retry, while fallback adds one assistant message. No artificial 500 ms delay. Reload resets transcript, not necessarily tab identity. Unmount aborts fetch but cannot undo a committed server write.
- **R-14 — Verification:** Follow red–green–refactor per acceptance-linked task. Cover backend, MySQL uniqueness/concurrency, Redis limits, frontend adapter/lifecycle, privacy and retention; preserve applicable UI regressions and replace only superseded mock-default assertions. Record application automated/manual evidence separately from production infrastructure and privacy-policy sign-off. Integration test bootstrap must fail closed unless isolated test hosts, least-privilege test credentials, run-specific database/key namespaces and APP_ENV=testing are verified; neither a database named testing nor a Redis prefix alone proves isolation. Never reset/flush shared development or production resources. No application changes before approval, no automatic commits.

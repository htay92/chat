# 004 — Minimal SaaS chatbot UI requirements

Status: Original UI and avatar amendment authorized and implemented with partial manual verification. Speaker-name separation amendment is draft — awaiting review; no implementation of this amendment authorized.

## Scope and baseline

Restyle the existing welcome-page Vue 3 + TypeScript chatbot as a Minimal SaaS light interface. Feature 001 remains the behavioral baseline: [requirements](../001-chatbot-widget/requirements.md), [design](../001-chatbot-widget/design.md), [tasks and evidence](../001-chatbot-widget/tasks.md), and [acceptance](../001-chatbot-widget/acceptance.md). Its implementation was authorized in the session despite older draft labels; its T-08 manual verification is still incomplete. This feature neither rewrites that history nor marks those checks passed.

No external AI, Laravel chat APIs, database changes, persistence, chat network requests, suggested-question behavior, or provider changes. The existing temporary local echo remains a frontend demo, not a production answer system. Predefined Q&A and API integration are outside this feature.

## Numbered requirements

1. **R-01 — Preserve integration and behavior.** Retain the reusable, duplicate-safe `mountChatbot()` and welcome-page-only mount. Preserve Laravel routes, Blade content, existing Vite entries/plugins, website CSS and JavaScript behavior. Preserve the typed injected `ChatResponder`, fixed 500 ms local mock, all existing validation, transcript, pending, retry, focus, cleanup, and no-network contracts. No module relocation or dependency additions are required. Derive avatar presentation from the existing message role; do not change message data, the mock responder, validation or API architecture.
2. **R-02 — Theme.** Use primary blue `#2563EB`, white panel/composer, slate secondary surfaces, and inherited website font. Maintain a light widget even on a dark host page. Panel maximum outer width is 380 CSS px with 20 px outer corner radius. Use subtle decorative borders and soft shadows; scope every style/token to the widget.
3. **R-03 — Launcher and header.** Provide a 56×56 CSS px circular blue launcher with a centered decorative chat icon and accessible name “Open chat”. Retain expanded state and panel reference. Header contains a decorative assistant icon, “Demo chatbot” heading, visible “Demo” badge, and accessible Close control. Retain the exact persistent notice “Demo only — responses are mocked.”
4. **R-04 — Messages and composer.** Right-align white-on-blue user bubbles and left-align slate assistant bubbles, with 16 px bubble radii. Display the exact name “Assistant” above each assistant bubble and “You” above each user bubble, outside the bubble, in 12–13 px semibold text. Assistant names/bubbles align left; user names/bubbles align right. Use 4–6 px vertical spacing between each name and bubble (design default: 13 px, weight 600, 5 px gap). Bubbles contain only the message text; speaker names are separate presentation elements, not part of message data. Each assistant message displays a circular bot avatar on the left of its bubble; each user message displays a circular user avatar on the right. Avatars are exactly 36×36 CSS px: assistant background #DBEAFE/icon #2563EB; user background #E2E8F0/icon #334155. Use simple Lucide-style local outline icons, align each avatar with the top of its message bubble, and keep an 8 px horizontal gap; place the speaker name above the bubble column. Reserve avatar/gap space without shrinking avatars or overflowing narrow screens. Preserve chronological DOM order, plain text, internal newlines and safe wrapping. Use a modern rounded composer with visible Message label, white rounded textarea and blue Send button. Keep exact existing status, validation, failure, empty-state, and Retry wording and semantics.
5. **R-05 — Responsive layout.** Retain 16 px viewport margins plus safe-area offsets, with a 12 px gap between launcher and panel. Bound panel height to available viewport space. At 320×568 and 1440×900 CSS px, 200% zoom, and a 320 CSS px reflow width, introduce no horizontal page overflow. Transcript scrolls independently; header/composer and Retry remain reachable. On mobile, accommodate virtual-keyboard viewport changes and safe areas; permit vertical panel scrolling in unusually short viewports rather than clipping controls.
6. **R-06 — Accessibility.** Meet applicable WCAG 2.2 AA criteria: normal text contrast ≥4.5:1, large text ≥3:1 (at least 24 px regular or approximately 18.7 px bold), and required control boundaries/state indicators ≥3:1 against adjacent colors. Keep visible, unobscured focus with a ≥3:1 indicator. Launcher is 56 px; Close/Send/Retry targets remain ≥44×44 CSS px. Decorative borders need not meet control contrast. Preserve non-modal dialog/log/status/alert semantics, error association, keyboard/IME behavior, and ordinary page navigation. Message avatars are decorative, non-interactive and non-focusable; hide their wrappers/icons from screen readers to avoid duplicate speaker announcements. Keep visible, accessible You/Assistant names outside bubbles and polite speaker-identifying message announcements. Expose each name once before its message in the accessible reading sequence; do not hide the name or duplicate it through an extra aria-label, hidden label or live region. The 36 px decorative avatars are not interactive targets and do not change the 44 px control requirement.
7. **R-07 — Focus and lifecycle.** Open idle/failed panel focuses Message; reopen pending focuses Close. Before valid Send or Retry disables composer controls, focus the stable panel. Invalid submission focuses Message and retains its draft. Failure re-enables composer; Retry resends the failed input without duplicating its user entry. Close returns launcher focus without cancelling pending work; completion never steals focus. Unmount aborts local timers, ignores stale/disposed results and handles late rejections.
8. **R-08 — Motion and infrastructure.** Reuse Instrument Sans through the existing font inheritance, Tailwind/Vite pipeline and namespaced `widget.css`. Local inline SVG icons must be decorative and non-focusable; add no icon library, remote assets or font requests. Optional transitions are limited to 120 ms color/shadow changes; reduced-motion disables them. No required entrance, pulsing, or bouncing animation.
9. **R-09 — Verification.** Preserve existing behavioral tests and add acceptance-linked visual-structure tests before implementation. Use the existing `test:frontend` and `typecheck` scripts. Record automated results separately from measured browser and actual screen-reader evidence; jsdom cannot establish layout, contrast or spoken announcements. Unperformed checks remain pending.
